## A-2. Stale-cache design REJECTED → live-source failover (Jesse design correction, mid-task)
- **WHAT:** the original brief included a last-good-scan disk cache (.scan-cache.json) served with a "stale Xmin" note. Jesse explicitly rejected serving last-known data on a money dashboard.
- **ROOT CAUSE (of the bad design):** stale balances on a trading screen can misprice a live decision; a "stale" label does not make the number safe to act on.

  Failover tiers proven live: Alchemy-RH answered with 13 nonzero token balances; raw-RPC balanceOf returned balances identical to Blockscout's numbers, token for token.
- **PREVENTION (doctrine):** **money data is live or explicitly errored, never silently stale.** No disk-cache code path exists to regress into; the failover chain is the only fallback mechanism.

# Data-Layer Fixes, round 2 — CW-sessionB-datafix (2026-07-21, later same day)

## E. Wallet values frozen — one cached blob served for minutes while the UI polls every 30s
- **WHAT Jesse saw (live):** portfolio value and wallet balances sat frozen on screen even though the UI polls /api/state every 30s.
- **ROOT CAUSE:** /api/state was one monolithic blob: every refresh re-ran the ENTIRE pipeline (balances + prices + orders + chain-history gap-fill + basis math). The heavy chain-history lane (15-min cache, ~100s+ rebuild on expiry) and slow serial calls made full rebuilds so slow that the server's serve-stale-while-refreshing blob cache kept handing out the same old numbers poll after poll. Cheap facts (balances, prices) were hostage to expensive facts (tx history).
- **FIX:** two-lane pipeline in datasource.mjs:
  - **FAST lane (~30s TTL, single-flight):** wallet token+native balances + current prices + portfolio value. Batched: ONE DexScreener call per ≤30 contracts (was one call per position), Alchemy token metadata cached forever (immutable), balance calls already cheap. On TTL expiry the lane does a LIVE fetch with retries/failover — expired data is never served without a live attempt (same doctrine as fix A-2).
  - **ORDERS lane (120s TTL):** the 1inch book. **Rate-cap note (required disclosure): a 30s cadence would breach the 1inch dev-tier cap** — 4 calls per refresh × 30s = ~172K calls/mo if the dashboard stayed open 24/7, over the 100K/mo free tier. 120s is the fastest cadence that stays safely under (~86K/mo worst-case). Fills therefore surface within ≤2 min, balances/prices within ≤30s.
  - **HEAVY lane (unchanged 15-min):** chain tx-history swap-scan, counter-leg lookups (cached forever per tx), token-age lookups (cached forever). Basis/lots math is in-memory and re-assembled on every request from fresh balances + cached heavy artifacts.
  - `/api/state` now merges fresh-over-heavy and carries per-section stamps: `freshness.pricesAt` (fast), `freshness.ordersAt` (orders), `freshness.scanAt` (heavy) — the UI can show an honest "updated Xs ago" per section.
  - dashboard-server.mjs blob ttl 25s → 5s: it is now only a request-coalescing layer (stops N tabs stampeding buildState); real freshness lives in the lanes.
  - Restart preserved Jesse's ARMED state (`env TRADE_IDEA_ARMED=1`, log at ~/Library/Logs/trading-dashboard.log); /api/trade-idea/config verified `armed:true` after restart.
- **PREVENTION:** cheap facts and expensive facts can never share one expiry again — each lane owns its TTL and its rate budget, and any future data added to the state must be assigned to a lane (and a cap check) explicitly. Per-section stamps make any future freeze immediately visible on the dashboard instead of silent.

# Ledger reconciliation — CW-sessionB-cbdex (2026-07-21)

## G. Coinbase retail-DEX ("DEX feature") trades invisible to the ledger
- **WHAT:** Jesse's Coinbase-app onchain trades never appeared in trades-ledger. Known symptom: a wallet received a token from a Coinbase-app onchain buy with no matching buy row, so the position showed a sell with no buy. (Quantity redacted for this release.) Adding 0xb92fe925…4fff4f as a watch wallet still yielded 0 swaps.
- **ROOT CAUSE (two-part):**
  1. **The watched address is not Jesse's wallet at all.** 0xb92fe925… is Relay Protocol's **RelayRouterV3** (Blockscout-verified name on Robinhood Chain; same deterministic address on Base) — shared execution infrastructure with ~101K txs on Base, almost all other users' trades. Coinbase's DEX feature settles through it: a relay solver (0xf70da978…) funds the stable money leg into the router, a settler routes the pools, and the router forwards the bought token to the user's wallet — all in ONE tx whose sender is a bundler. The router's own history nets to ZERO on every tx (pure pass-through), so scanning it as a wallet finds no swaps ever.
  2. **Same-sender leg pairing can't see these fills.** From wallet-2's perspective the tx has exactly one leg (token IN); sources/base.mjs + robinhood.mjs classify single-leg txs as deposits/airdrops (correctly for real deposits), so the buy — whose money leg was paid by the solver, not the wallet — was skipped.
- **FIX (ledger/ only):** new `ledger/lib/router-swaps.mjs` + step (3) in `ledger/sources/base.mjs`. Wallets flagged `"router": true` in ledger-config.json (coinbase-dex-wallet corrected + flagged) are never full-scanned; instead the ingest pulls only the router↔trackedEOA transfer intersection (both directions, erc20+external+internal, full pageKey pagination), then re-reads each such tx's FULL receipt log set and classifies leg-based per tx hash, sender-agnostic: wallet receives token + router receives stable in same tx = BUY (cost = solver's stable, exact); wallet sends token + stable comes back = SELL; same-token pass-through / stable-only hops = bridge transfers, skipped. Ids reuse `base:tx:<hash>` so re-runs add 0 (verified: full ingest ×2, +0/+0). Result: the missing DEX-tab buy (exact token quantity, exact USDC cost, exact timestamp) is now in the ledger, recovered entirely from receipt logs; re-running the ingest adds zero duplicates. (Fill details redacted for this release.)

## 2026-07-27 — "it should NEVER open with stale stuff. Every time I press refresh, it should refresh." (Jesse)

**Root cause (verified by reading the code, not guessed).** `cached()` in `dashboard-server.mjs`
was UNCONDITIONAL stale-while-revalidate:

```js
if (c.data) return { data: c.data, stale: true };   // serve old, rebuild in background
```

Any request past the 5s ttl got the PREVIOUS snapshot and merely kicked a background
rebuild. The fresh data therefore landed on the NEXT press, never the current one. So:
- First paint always rendered whatever the cache last held, however old.
- Pressing "refresh now" always showed the pre-refresh snapshot. Jesse's exact complaint.
- A 200 on `/` proved only that the HTTP server was answering. It said nothing about the
  data path, which is why a dead refresh loop looked healthy from outside.

**Second defect found in the same log.** 261 × `funding refresh failed, serving stale:
funding-calc: bad JSON output`. The funding panel had been serving last-good numbers
indefinitely with NOTHING surfaced in the UI. A permanently failing rebuild was invisible.

**Fix.**
1. `cached()` now takes `{force}` and each slot has a `maxStale` ceiling. Three bands:
   `age < ttl` serve cache (coalescing, unchanged) · `ttl..maxStale` stale-while-revalidate
   · `age > maxStale` AWAIT the rebuild. state maxStale 60s, funding 600s.
2. `/api/state` and `/api/funding` accept `?fresh=1` → force, and now return `ageMs` +
   `refreshError` so staleness and failure are reportable instead of silent.
3. `dashboard.html`: `loadState(force)` / `loadFunding(force)`; the refresh button passes
   force, disables itself, shows "refreshing…", and the header shows "pulling live data…";
   FIRST PAINT passes force so the cockpit cannot open on a stale snapshot.
4. Funding now renders a visible `⚠ funding refresh failing: <msg> · last good Nm ago`.
